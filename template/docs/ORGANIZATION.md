# 組織と実行ルート

CLAUDE.md の補足。部門の詳しい振る舞いは .claude/agents/*.md が正。ここは Root が判断に使う規則をまとめる。

## 部門の責任と評価
| 部門 | 入力 → 成果物 | 報告が必要なとき | 評価の基準 |
|---|---|---|---|
| 企画 | 市場の課題・技術で省ける工程・既存資産・競合の穴・販売後の反応 → 比較と推奨案 | 前提が崩れた、枠を超える | 企画の数ではなく、販売実験への到達と、売上/反応からの学び |
| マーケティング | 企画仮説・観測データ → 競合/無料代替比較、集客経路、販売分析 | 経路が成立しない、重大な反応 | 流入、第三者購入、返金、工数、学び |
| 商品開発 | 採用仕様・枠・品質条件 → 商品、説明、手順、自己検証、修正版 | 仕様から外れる、実現困難、枠超過 | 実物と説明の一致、欠陥の少なさ、制作/対応負荷 |
| 品質管理 | 固定した版・説明・証拠 → 合否、修正要求、解除条件 | 重大問題は即時 | 再現できる指摘、重大な見逃しの無さ |

経理はRootが兼務。ledger/REVENUE.md に 売上/手数料/返金/経費/利益/Owner時間 を分けて記録する。

## 品質ゲート
- **重大**：中核機能が使えない、データ損失、秘密や有料部分の露出、説明と実物の重大な不一致、権利問題。→ 品質管理が対象版を公開差止め。開発が修正 → 品質管理が再検証 → 解除。
- **軽微**：利用を妨げない誤字・表記・表示。→ Rootがリスク・受容理由・期限を記録して判断。
- **不明**：重大の疑いが合理的にあるときは一時保留して限定確認。好みだけで止めない。
- 指摘には「対象版 / 証拠 / 再現手順 / 影響 / 重大度 / 解除条件」を付ける。
- 判定に異議があるときは、別の独立レビュー（もう一度 quality-control を新規起動、または別のAI（相手社）へ依頼）で再評価。決着まで差止めを維持。
- 小さな内部資料や可逆で影響の小さい作業は Root の確認で足りる。

## 実行ルート
※ ルート1の企画段階は docs/PLANNING_CRITERIA.md の「進め方」と審査基準に従う。

優先順：重大な品質/安全問題 → 実行を阻む障害 → 既存案件の残工程 → 販売後の判断 → 新規企画。
選んだルート・根拠・今回の完了条件・次工程・必要担当・承認ゲートを案件記録に短く残す。全ルートを回す必要はない。

1. **新規商品**（商品や販売仮説が未確定）
   planning で探索 → 必要なら marketing（需要/経路）・product-development（実現性）で確認 → Root採否（重要採用はOwner）→ 最小制作 → quality-control → Owner公開承認 → 公開 → 観測。公開の証拠で「販売検証開始」とし、売上とは区別する。
2. **丸投げ**（目標と制約だけ渡された）
   Rootが完了条件と残工程を具体化し、合理的な仮定は記録して進める。質問は不可欠なものだけ。状態に応じて 1/3/4/5 に分解。計画や委任ができただけで完了扱いにしない。
3. **再開**（成果物や進捗がある）
   最新版・証拠・承認を実際の状態と照合し、最初の未完工程から。完成済み商品なら企画や制作に戻らず、設定・プレビュー・承認・公開へ。品質確認は変更差分に限定。
4. **障害**（工程を妨げる失敗）
   失敗した操作・エラー・観測と、原因仮説を分ける。正式な代替手段を 成功見込み/時間/費用/認証負担/品質/権限 で比較し、承認範囲内で切替えて元の工程へ戻る。同じ条件の失敗を理由なく繰り返さない。認証情報の抜き出し・制限回避は代替にしない。
5. **販売後**（公開済み・反応あり）
   marketing が 期間/流入/第三者購入/返金/質問/費用/工数 を分析 → 品質原因は quality-control、修正は product-development → Root が継続/改善/停止/再企画を判断。データ取得前に継続/停止を判断しない。

## Ownerへの依頼
具体的な承認・本人にしかできない操作・重大リスクだけをまとめて出す。本人操作には「理由 / 完全な手順 / 素材 / 所要時間 / 返却してほしいもの」を付ける。所要時間を記録する。

## チェックポイント（判断の区切り・外部操作の直後・中断時に保存）
案件の STATUS 欄へ：完了条件、ルートと根拠、成果物の版とパス、実施済みと証拠（URL/ID/時刻）、未検証、承認範囲と出典、品質ゲート、障害と試した経路、判断、次の具体操作、Owner時間/費用の観測、学び。
公開・投稿・支払が実施済みか不明なときは、現状態を確認してから再操作する（二重実行防止）。

## 実行方式の選び方
並列化は目的にしない。依存関係・作業規模・文脈量・トークン/起動コスト・品質・Owner確認回数で選ぶ。小さな作業は分割しない。
| 方式 | 向く作業 | 実環境での確認 |
|---|---|---|
| Root単独 | 短い統合・記録・判断 | — |
| 部門の別セッション `claude -p --agent <部門>`（バックグラウンド） | 独立した調査・比較の並列、部門定義のツール制限を効かせたい作業 | 筆者の環境で動作確認済み |
| 汎用サブエージェント（Agent tool） | Rootの文脈を引き継ぎたい中規模作業 | 利用可 |
| Agent Teams / Git worktree | 同じリポジトリで複数セッションが並行して編集するとき | 未確認。使う前に確認し、使えなければ書込み先フォルダの分離で代替 |
委任文には必ず：目的 / 入力資料 / 担当範囲（書込み先） / 成果物 / 完了条件 / 禁止事項。統合と最終判断はRoot。
別セッションの成果は experiments/<案件>/ に保存し、案件記録に「状態・決定・未完了・次の一手」を残して、再開時に同じ調査を繰り返さない。並列化の効果と問題は ledger/LEARNINGS.md に記録する。
